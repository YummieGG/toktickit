# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Deliver a Requester-facing IT support ticketing MVP that allows users to create tickets, view their tickets, and manage attachments, using a temporary Development Requester selector for testing.

## 2. Stakeholder Request
The stakeholder wants a responsive, Zen Green-themed web portal for Requesters to create IT support tickets by providing problem details, category, related system, requested priority, and attachments. Requesters must be able to view, search, and manage only their own submitted tickets, isolated from other users, using a temporary Development Requester selector for multi-user testing.

## 3. Scope
### Included
- Development Requester Selection (simulated login)
- Create Ticket with validation and attachments
- My Tickets with search, filter, sort, pagination
- Requester Ticket Detail (read-only)
- Attachment lifecycle (upload, download, soft-remove)
- Ownership protection (requester can only see own tickets)
- Zen Green Theme and responsive UI
- REST API with validation and error handling
- PostgreSQL database with Prisma ORM

### Excluded
- Authentication/security (login, passwords, sessions, tokens, roles)
- IT Staff workflow (dashboard, claiming, reassigning, IT Priority changes)
- Ticket collaboration (Public Comments, Internal Notes, Actions Taken)
- Ticket lifecycle beyond initial 'New' status
- Administration functions

## 4. Functional Requirements
- **FR-01**: System shall display a Development Requester Selection screen.
- **FR-02**: System shall load active requesters from the database.
- **FR-03**: System shall allow requester switching with data reload.
- **FR-04**: System shall display Create Ticket form with required fields.
- **FR-05**: Ticket Number auto-generated by backend (format: TK-XXXX, auto-increment).
- **FR-06**: Ticket Date auto-generated by the system upon creation.
- **FR-07**: Category dropdown loaded from DB (active only).
- **FR-08**: Related System dropdown loaded from DB (active only, optional field).
- **FR-09**: Requested Priority selection (LOW, MEDIUM, HIGH, CRITICAL).
- **FR-10**: Summary field (required, 5-200 chars).
- **FR-11**: Description field (required, 10-2000 chars).
- **FR-12**: Attachment upload during creation (optional).
- **FR-13**: Validation on both frontend and backend.
- **FR-14**: Success state shows generated Ticket Number.
- **FR-15**: My Tickets shows only selected requester's tickets.
- **FR-16**: Search across ticket number, summary, description.
- **FR-17**: Filter by category, status, priority.
- **FR-18**: Sort by ticket date, ticket number, summary.
- **FR-19**: Pagination with configurable page size.
- **FR-20**: Ticket Detail shows read-only ticket info.
- **FR-21**: Ticket Detail shows attachment list.
- **FR-22**: Add attachment to existing ticket.
- **FR-23**: Download active attachment.
- **FR-24**: Soft-remove attachment with reason.
- **FR-25**: Ownership check on all requester-specific endpoints.

## 5. Business Rules
- **BR-01**: Ticket Number generated by backend, unique, format TK-XXXX (auto-increment, zero-padded to 4 digits).
- **BR-02**: New Ticket begins with Current Status 'NEW'.
- **BR-03**: Dev Requester selector is a testing mechanism, not authentication.
- **BR-04**: Only active requesters appear in the selector.
- **BR-05**: Inactive requesters cannot create tickets.
- **BR-06**: Requester can only view/access own tickets.
- **BR-07**: Switching requester reloads all requester-specific data.
- **BR-08**: Allowed attachment types: JPG/JPEG, PNG, WEBP, PDF.
- **BR-09**: Max attachment size: 5 MB per file.
- **BR-10**: Max 5 active attachments per ticket.
- **BR-11**: Soft removal: file remains as metadata, not downloadable.
- **BR-12**: Removal requires confirmation and reason.
- **BR-13**: Removed attachment metadata still visible (filename, upload date, removed status).
- **BR-14**: Summary trimmed of leading/trailing whitespace.
- **BR-15**: Description trimmed of leading/trailing whitespace.
- **BR-16**: Default sort: ticket date descending.
- **BR-17**: Default page size: 10.
- **BR-18**: Permitted page sizes: 5, 10, 20.
- **BR-19**: Submit button disabled during submission (prevent double submit).
- **BR-20**: Form data preserved on API failure.
- **BR-21**: Empty state shown when requester has no tickets.
- **BR-22**: No-results state shown when search/filter yields nothing.
- **BR-23**: Ticket Date is set server-side at creation time.
- **BR-24**: Category is required for ticket creation.
- **BR-25**: Related System is optional for ticket creation.

## 6. UI Specification Summary
The UI will feature an application shell with TokTickIT branding, navigation links, and a display of the currently selected requester. The "Create Ticket" form will have a clean layout for data entry, while the "My Tickets" view will utilize a list or table layout suitable for displaying ticket information. The "Ticket Detail" view will be read-only, presenting ticket information clearly. Attachment states will be visually distinct. The application must be responsive across breakpoints (desktop ≥992px, tablet 768-991px, mobile <768px).
*Reference to `docs/lab-02/ui-spec.md` for full details.*

## 7. Data Changes
### Models
- **RequesterUser**: `id`, `name`, `email` (unique), `isActive`, `createdAt`, `updatedAt`
- **Category**: `id`, `name` (unique), `isActive`, `createdAt` (expand existing model)
- **RelatedSystem**: `id`, `name` (unique), `isActive`, `createdAt`
- **Ticket**: `id`, `ticketNumber` (unique), `summary`, `description`, `requestedPriority` (enum), `currentStatus` (enum, default NEW), `ticketDate`, `createdAt`, `updatedAt`, `requesterId` (FK), `categoryId` (FK), `relatedSystemId` (FK, nullable)
- **Attachment**: `id`, `originalName`, `storedName`, `mimeType`, `sizeBytes`, `isRemoved`, `removalReason` (nullable), `removedAt` (nullable), `createdAt`, `ticketId` (FK)

### Enums
- **TicketStatus**: `NEW`
- **RequestedPriority**: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`

### Relationships
- `RequesterUser` 1→N `Ticket`
- `Category` 1→N `Ticket`
- `RelatedSystem` 1→N `Ticket` (optional)
- `Ticket` 1→N `Attachment`

### Indexes
- **Ticket**: `requesterId`, `currentStatus`, `categoryId`
- **Attachment**: `ticketId`
- **Unique**: `ticketNumber`, `email`, category `name`, related system `name`

### Seed Data
- 4 Categories: Account and Access, Hardware, Software, Network
- 6 Related Systems: Email, Campus Wi-Fi, VPN, LEB2 App, Grade Submission App, Printer
- 4 active Requesters (realistic Thai names/emails)
- 1 inactive Requester

### Design Decision
Auto-increment integer IDs are used for simplicity. The ticket number is formatted as TK-XXXX for readability. Soft removal is implemented on attachments rather than hard delete to preserve an audit trail. File storage utilizes the local filesystem (`uploads/` directory) for simplicity, with files stored using UUID-based names to prevent collisions.

## 9. Acceptance Criteria
- **AC-01**: Given active requesters exist, when page loads, then requester dropdown shows only active requesters.
- **AC-02**: Given requester selected, when Continue clicked, then app shell shows requester name and navigates to My Tickets.
- **AC-03**: Given requester selected, when Create Ticket opened, then form shows required fields with categories and systems loaded from DB.
- **AC-04**: Given valid ticket data entered, when Submit clicked, then ticket is created and unique Ticket Number displayed.
- **AC-05**: Given invalid data (empty summary), when Submit clicked, then validation message appears near the field.
- **AC-06**: Given ticket created, when My Tickets opened, then new ticket appears in the list.
- **AC-07**: Given Requester A selected, when viewing My Tickets, then only Requester A's tickets are shown.
- **AC-08**: Given Requester A's ticket exists, when Requester B tries to access it directly, then access is denied.
- **AC-09**: Given tickets exist, when search term entered, then matching tickets are shown.
- **AC-10**: Given tickets exist, when filter applied, then only matching tickets shown with clear filters option.
- **AC-11**: Given multiple tickets, when sort changed, then list order updates.
- **AC-12**: Given many tickets, when navigating pages, then pagination works correctly with metadata.
- **AC-13**: Given ticket detail opened, when viewed, then all ticket info is read-only.
- **AC-14**: Given ticket with < 5 attachments, when valid file attached, then file uploads and appears in list.
- **AC-15**: Given invalid file type attached, when upload attempted, then clear error shown.
- **AC-16**: Given file > 5MB attached, when upload attempted, then size error shown.
- **AC-17**: Given ticket with 5 active attachments, when upload attempted, then max limit error shown.
- **AC-18**: Given active attachment, when download clicked, then file downloads.
- **AC-19**: Given active attachment, when remove clicked, then confirmation with reason is required.
- **AC-20**: Given removed attachment, when viewing detail, then metadata visible but download blocked.
- **AC-21**: Given backend down, when any action attempted, then safe error state shown with data preserved.
- **AC-22**: Given no tickets for requester, then empty state message shown.
- **AC-23**: Given search with no results, then no-results state shown.
- **AC-24**: Given any screen, when viewed at desktop/tablet/mobile, then layout is responsive with no clipping.

## 11. Assumptions and Decisions
- Ticket Number uses auto-increment format TK-XXXX (zero-padded).
- File storage uses local filesystem (`uploads/` directory) with UUID-based filenames.
- Related System is optional when creating a ticket.
- Default pagination: page 1, size 10.
- Session storage used to persist selected requester (not cookies/localStorage for security).
- Lab 2 TicketStatus enum only contains `NEW` (future statuses added in later labs).
- The Development Requester model will be replaced/evolved when real auth is introduced in Lab 3.
